# Инструкция по заполнению базы ManagerSL

Эта инструкция для администратора ManagerSL, который впервые заходит в Django Admin и заполняет базу для новой ERP/CRM/HRM системы.

## 1. Вход в админку

- Админка доступна по адресу `/admin/`.
- Обычные сотрудники работают через `/portal/`.
- Доступ к админке должен быть только у superuser, staff и сотрудников, которым явно разрешено управление системой.
- Заголовок админки: **ManagerSL — Администрирование**.

## 2. Какие разделы использовать

Для ежедневной работы используйте новые разделы:

1. **Организация**: компании, офисы, отделы, должности.
2. **Сотрудники**: пользователи, профили сотрудников, роли, доступы, рейтинг.
3. **CRM**: потенциальные клиенты, лиды, клиенты, заявки, активности, заметки, файлы.
4. **ВУЗы и программы**: страны, города, валюты, ВУЗы, программы, стоимость, intakes, документы, контакты ВУЗов.
5. **Услуги**: категории услуг, услуги, цены услуг.
6. **Финансы**: кассы, сделки, доходы, расходы, платежи, транзакции, комиссии, периоды.
7. **Документы**: шаблоны, поля шаблонов, сгенерированные документы, подтверждения, печати, логи скачиваний.
8. **Рабочий день**: рабочие дни, сессии, ежедневные отчёты, напоминания.
9. **Проекты и задачи**: проекты, разделы, задачи, комментарии, чек-листы, файлы.
10. **База знаний**: папки, статьи, вложения, прочтения.
11. **Уведомления**: уведомления, шаблоны, логи, device tokens.
12. **Настройки**: пользовательские поля, варианты, значения и группы прав.

Старые приложения `clients`, `leads`, `catalog`, `services`, `analytics`, `documents`, `tasks`, `timetracking`, `notifications`, `reports`, `mailing`, `gamification`, `support` оставлены только для миграций и совместимости. Обычный staff их не видит. Superuser может открыть их как **Архив / Старые данные**, если нужно проверить старую запись или перенос данных.

## 3. Порядок первичной настройки

1. Создайте компанию в разделе **Организация / Компании**.
2. Создайте офисы и обязательно привяжите каждый офис к компании.
3. Создайте отделы.
4. Создайте должности.
5. Создайте роли сотрудников.
6. Создайте пользователей в разделе **Сотрудники / Пользователи**.
7. Для каждого пользователя создайте **Профиль сотрудника**.
8. В профиле укажите компанию, офис, отдел, должность, роль, телефон и дату рождения.
9. Если сотрудник должен участвовать в рейтинге, включите настройку **Показывать в рейтинге** в доступах/профиле сотрудника.
10. Проверьте, что у сотрудника есть нужные права staff или доступ к порталу.

Если не создать `EmployeeProfile`, портал не сможет правильно подставлять компанию, офис, рабочий день, клиентов и права доступа.

## 4. Как заполнить ВУЗы

Рекомендуемый порядок:

1. Создайте страну.
2. Создайте город и привяжите его к стране.
3. Создайте валюту. Для основной системной валюты используйте `USD` с курсом `1`.
4. Создайте ВУЗ.
5. В карточке ВУЗа заполните основные данные, контакты, описание, требования, общежитие, расходы и возрастные ограничения.
6. Внизу карточки ВУЗа добавьте программы через inline-блок **Программы**.
7. Рядом с программой сразу заполните основные цены в USD: **Стоимость программы**, **Стоимость услуг**, **Application fee**, **Общежитие**, **Страховка**.
8. Если нужно добавить intakes или документы конкретной программы, откройте программу через ссылку изменения. На странице программы эти данные добавляются inline-блоками.
9. Добавьте контакты ВУЗа через inline-блок в карточке ВУЗа.

Важно: ВУЗ можно сохранить без программы. Если программа уже известна, добавьте её сразу в inline-блоке **Программы** и рядом заполните стоимость обучения и стоимость услуг в USD. Если программа ещё не готова, сохраните ВУЗ, а программу добавьте позже через карточку ВУЗа или раздел **Программы обучения**. Стоимость программ в рабочей админке заполняется через ВУЗ или программу, отдельный раздел стоимости программ для ежедневной работы не используется. Срок действия стоимости больше не заполняется.

### Импорт программ из JSON

Если программ много, их можно загрузить через админку:

1. Откройте **ВУЗы и программы / Программы**.
2. Нажмите кнопку **Импорт программ из JSON**.
3. Сначала оставьте включённым **Тестовый импорт / dry-run** и загрузите файл.
4. Проверьте отчёт: сколько строк прочитано, сколько будет создано/обновлено, какие строки пропущены.
5. Если ошибок нет, снимите dry-run и повторите импорт.

Файл может быть обычным JSON-массивом или набором JSON-объектов через запятую без внешних квадратных скобок. Университеты должны быть созданы заранее: импорт не создаёт ВУЗы автоматически, чтобы случайно не завести неполные карточки без страны, города и валюты. Дубли определяются по связке **ВУЗ + название программы + степень + длительность**. Стоимость обучения попадает в `ProgramFee.tuition_fee`, стоимость услуг — в `ProgramFee.service_fee_usd`.

## 5. Как заполнить услуги

1. Создайте категорию услуги.
2. Создайте услугу.
3. Укажите название, код, описание и категорию.
4. Укажите цену для клиента.
5. Укажите себестоимость. Это внутреннее поле, его не нужно показывать клиентам.
6. Выберите валюту, обычно USD.
7. Отметьте, активна ли услуга и видна ли она сотрудникам.

Услуги можно добавлять и через web cabinet: `/portal/services/`.

## 6. Как добавить клиента

Минимально нужны:

- ФИО;
- телефон или email;
- направление / интерес.

Остальные поля необязательные, но полезны для документов:

- дата рождения;
- гражданство;
- город;
- адрес проживания;
- адрес регистрации;
- внутренний паспорт;
- загранпаспорт;
- кем выдан паспорт;
- дата выдачи и срок действия;
- данные родственника;
- текущее образование;
- интересующая страна, ВУЗ и программа.

Обычный сотрудник в портале создаёт клиента на себя и свой офис. Администратор может вручную выбрать менеджера, офис и компанию.

## 7. Потенциальные клиенты и лиды

Старый endpoint `/api/leads/create/` сохранён для внешнего сайта. Сайт должен отправлять заголовок `X-API-KEY`, а ключ хранится только в `.env` как `LEADS_API_KEY`.

Новые заявки попадают в CRM как **Потенциальные клиенты**:

1. Менеджер открывает `/portal/incoming-leads/`.
2. Нажимает **Взять ответственность**.
3. Заявка закрепляется за менеджером и его офисом.
4. Если менеджер взял заявку случайно и клиент ещё не создан, он может нажать **Вернуть в потенциальные клиенты**.
5. После обработки менеджер создаёт клиента по лиду, чтобы не вводить ФИО, телефон, email и направление повторно.

Лиды не удаляются физически из портала. Их нужно переносить в архив. Обычный сотрудник архивирует только свои лиды, администратор может архивировать и восстанавливать любые.

## 8. Как создать шаблон документа

1. Откройте раздел **Документы / Шаблоны документов**.
2. Создайте новый шаблон.
3. Заполните название, тип документа, описание и активность.
4. Загрузите DOCX-файл.
5. В DOCX используйте Jinja-переменные, например:
   - `{{ client.full_name }}`
   - `{{ client.phone }}`
   - `{{ client.email }}`
   - `{{ client.passport_inter_num }}`
   - `{{ client.passport_issued_by }}`
   - `{{ client.passport_issued_date }}`
   - `{{ client.address_registration }}`
   - `{{ application.university_name }}`
   - `{{ application.program_name }}`
   - `{{ company.name }}`
   - `{{ office.city }}`
   - `{{ manager.first_name }}`
   - `{{ manager.last_name }}`
6. Добавьте поля шаблона через inline **DocumentTemplateField**. JSON вручную заполнять не нужно.
7. Укажите, можно ли скачивать DOCX без печати.
8. Укажите, можно ли скачивать PDF с электронной печатью.
9. Укажите, требуется ли подтверждение администратора.
10. Если нужен PDF с печатью, настройте правило печати: изображение, ширина/высота в мм, позиция, x/y для custom.
11. Если нужен водяной знак, включите его и укажите текст/изображение, прозрачность, позицию и размер.

Если печать не настроена, портал должен показать понятную ошибку: **Для этого шаблона не настроена электронная печать**.
PDF с печатью создаётся так: готовый DOCX конвертируется в PDF через LibreOffice, затем электронная печать накладывается на существующую страницу PDF. По умолчанию печать ставится на последнюю найденную строку со словом **Исполнитель**. Если такой строки нет, используется позиция из правила печати.

Для корректной кириллицы на сервере должны быть установлены LibreOffice и шрифты с поддержкой русского/туркменского текста, например `fonts-dejavu` или `fonts-liberation`.

## 9. Как генерировать документы

1. Откройте клиента в `/portal/clients/`.
2. Нажмите **Создать документ**.
3. Выберите шаблон.
4. При необходимости выберите заявку или сделку.
5. Проверьте данные клиента, менеджера, офиса, компании, ВУЗа и программы.
6. Создайте документ.
7. DOCX без печати можно скачать сразу, если это разрешено шаблоном.
8. PDF с печатью доступен только после подтверждения администратора.
9. Администратор подтверждает или отклоняет документы в `/portal/approvals/`.
10. Для печати администратор открывает **Проверить онлайн**, выбирает режим: автоматически на слове **Исполнитель**, вручную на листе или по правилу из админки.

История хранит, кто создал документ, когда создал, кто подтвердил, когда подтвердил, кто скачал и когда скачал.

## 10. Как работать с финансами

Валюта системы: **USD**.

1. Создайте сделку и выберите клиента.
2. Выберите услугу из базы или напишите название вручную.
3. Укажите цену в USD.
4. Добавьте платёж, если нужно.
5. Добавьте доход через портал или админку.
6. Доход после создания имеет статус **Ожидает подтверждения**.
7. Администратор подтверждает доход в `/portal/approvals/`.
8. После подтверждения доход учитывается в статистике и начисляет менеджеру комиссию 5%.
9. Повторное подтверждение не должно начислять комиссию повторно.
10. Расходы через портал учитываются как расходы сразу, но администратор видит их список.

### Доходы и кассы

1. Сначала создайте кассу в разделе **Финансы / Кассы**.
2. Для портала основная касса должна быть в валюте **USD**. Если USD ещё нет в валютах, создайте валюту `USD` с курсом `1`.
3. Кассу нужно привязать к компании и, если нужно, к офису.
4. Сотрудник добавляет доход в `/portal/finance/income/` или `/portal/finance/income/create/`.
5. В форме дохода сотрудник выбирает доступную ему USD-кассу.
6. Обычный сотрудник видит кассы своей компании/офиса, директор офиса видит кассы своего офиса, администратор видит все кассы.
7. Клиент, сделка и услуга в доходе необязательны. Их выбирают только если доход нужно связать с конкретным клиентом или сделкой.
8. Сумма дохода всегда вводится в USD.
9. После создания доход получает статус **Ожидает подтверждения**.
10. Администратор подтверждает доход в `/portal/approvals/`. Только после подтверждения доход попадает в финальную статистику и начисляет комиссию менеджеру.

Если у сотрудника доступна только одна USD-касса, она подставляется в форме автоматически.

### Уведомления

Администратор может отправлять уведомления сотрудникам из web cabinet:

1. Откройте `/portal/notifications/`.
2. Перейдите во вкладку **Создать уведомление** или нажмите кнопку **Создать**.
3. Заполните заголовок и текст.
4. Выберите тип уведомления: `info`, `success`, `warning` или `error`.
5. Выберите получателя:
   - один сотрудник;
   - офис;
   - все сотрудники.
6. Если выбран офис, укажите офис.
7. Если выбран один сотрудник, укажите сотрудника.
8. Нажмите **Создать уведомление**.

После отправки система создаёт рассылку и отдельное уведомление каждому получателю. Во вкладке **Отправленные** администратор видит статистику:

- **Получили**: сколько сотрудников получили уведомление.
- **Прочитали**: сколько сотрудников открыли или отметили уведомление прочитанным.
- **Не прочитали**: сколько сотрудников ещё не прочитали уведомление.
- **Процент прочтения**: доля прочитавших от общего количества получателей.

В деталях отправленного уведомления можно открыть список получателей и посмотреть статус каждого сотрудника. Обычный сотрудник видит только свои уведомления, может фильтровать их по статусу и отмечать как прочитанные.

## 11. Как работать с проектами

1. Создайте проект в `/portal/projects/` или в админке.
2. Система создаёт дефолтный раздел **Основные задачи**, если разделов нет.
3. Добавьте дополнительные разделы, если нужно.
4. Создайте задачу из карточки проекта или общего списка задач.
5. Укажите исполнителя, дедлайн, статус, приоритет и описание.
6. В задаче можно вести комментарии, чек-листы и файлы.

## 12. Как работать с базой знаний

1. Создайте папку.
2. При необходимости выберите родительскую папку.
3. Создайте статью внутри папки.
4. Добавьте текст, инструкции, ссылки и файлы.
5. Сотрудник может копировать текст статьи кнопкой **Скопировать текст**.
6. Удалять папки и статьи может только admin/staff/superuser.

## 13. Как работать с рабочим днём

1. Сотрудник начинает день на dashboard или странице `/portal/workday/`.
2. После старта появляются кнопки отчёта и закрытия дня.
3. До старта кнопка **Закрыть день** не показывается.
4. После закрытия показывается статус **Рабочий день закрыт**.
5. Обычный сотрудник видит только свою историю.
6. Администратор видит историю всех сотрудников и может фильтровать по офису, сотруднику и дате.

Рабочие старты и закрытия не отображаются в календаре. Календарь показывает события, дедлайны задач, дни рождения и важные даты.

## 14. Приоритет сотрудников в рейтинге

В разделе **Сотрудники / Права сотрудников** администратор может включить настройку **Приоритет в рейтинге**.

1. Включите **Приоритет в рейтинге**.
2. Укажите **Уровень приоритета в рейтинге**. Чем больше число, тем выше сотрудник будет отображаться.
3. При необходимости заполните **Комментарий к приоритету**.
4. Если приоритет выключен, сотрудник сортируется по обычным баллам.
5. Поле **Показывать в рейтинге** работает отдельно: если оно выключено, обычные сотрудники не видят этого сотрудника в рейтинге.

Бейдж приоритета видит только администратор. Обычный сотрудник не может включить себе приоритет самостоятельно.

### Кто обязан отмечать рабочий день

В профиле доступа сотрудника есть настройка **Обязан отмечать рабочий день**.

1. Включите её для менеджеров и сотрудников, которые должны ежедневно начинать день, отправлять отчёт и закрывать день.
2. Отключите её для владельца, бухгалтера, администратора или другого сотрудника, которому ежедневная отметка не обязательна.
3. Сотрудник с отключённой настройкой всё равно может отмечать рабочий день добровольно.
4. Такие сотрудники не попадают в список нарушителей и не штрафуются в рейтинге за пропущенный рабочий день.

### История отчётов сотрудника

Сотрудник может открыть `/portal/workday/reports/` и посмотреть свои прошлые отчёты: дату, статус дня, время начала, время закрытия и текст отчёта. Обычный сотрудник видит только свои отчёты. Администратор видит отчёты всех сотрудников и может фильтровать по офису, сотруднику и дате.

## 15. Проверка и одобрение документов

Когда менеджер отправил документ на подтверждение, администратор открывает `/portal/approvals/` и нажимает **Проверить онлайн**.

На странице проверки администратор видит:

- клиента;
- шаблон;
- автора документа;
- дату создания;
- статус;
- текстовый предпросмотр DOCX;
- кнопку скачивания DOCX без печати;
- кнопку **Подтвердить без печати**;
- блок **Сгенерировать / перегенерировать предпросмотр PDF с печатью**;
- кнопку **Открыть предпросмотр PDF**;
- кнопку **Подтвердить этот PDF для скачивания**, если предпросмотр уже создан;
- кнопку **Отклонить**.

Для печати есть три режима:

1. **Автоматически на слове “Исполнитель”** — режим по умолчанию. Система ищет последнюю строку с текстом “Исполнитель” и ставит печать поверх этой области. Если такой строки нет, используется позиция из правила печати.
2. **Выбрать область вручную** — администратор двигает область печати на листе в веб-интерфейсе и задаёт ширину/высоту в миллиметрах.
3. **По правилу из админки** — используется позиция, указанная в правиле электронной печати.

PDF с печатью подтверждается в два шага:

1. Администратор выбирает позицию печати и нажимает **Сгенерировать предпросмотр PDF**.
2. Администратор открывает предпросмотр PDF и проверяет, что печать стоит правильно.
3. Если печать стоит неправильно, администратор меняет позицию/размер и нажимает **Перегенерировать предпросмотр PDF**. Это можно делать сколько угодно раз, пока документ не подтверждён.
4. Когда всё выглядит правильно, администратор нажимает **Подтвердить этот PDF для скачивания**.

Только после финального подтверждения документ получает статус **Одобрен**, и у менеджера появляется скачивание PDF с печатью. Если в правиле печати включён водяной знак, он добавляется в PDF предпросмотра и в финальный PDF. Если печать для шаблона не настроена, портал показывает понятную ошибку: **Для этого шаблона не настроена электронная печать**. DOCX без печати при этом остаётся доступным.

## 16. Настройка электронной печати

Электронная печать настраивается в разделе **Документы / Правила электронной печати**.

1. Выберите компанию, офис и шаблон, если правило должно работать только для конкретного шаблона.
2. Загрузите файл электронной печати.
3. Укажите ширину и высоту печати в миллиметрах.
4. Выберите позицию печати: снизу слева, снизу справа, сверху слева, сверху справа, по центру или своя позиция.
5. Для своей позиции укажите координаты X и Y в миллиметрах.
6. Если нужен водяной знак, включите его, укажите текст или изображение, прозрачность, позицию и размер.

Для PDF с печатью у шаблона документа должно быть включено **Разрешить скачать с печатью**, а документ должен быть одобрен администратором.

## 17. Уведомления о днях рождения

Система может отправлять уведомления за день до дня рождения сотрудника в 08:00 по часовому поясу Asia/Ashgabat.

Получатели:

- сотрудники того же офиса;
- администраторы и superuser.

Команда для ручного запуска:

```bash
python manage.py send_birthday_reminders
```

Команда защищена от дублей: если уведомление за конкретный день уже отправлено конкретному получателю, повторно оно не создаётся.

Если Celery Beat запущен, задача выполняется автоматически каждый день в 08:00. Если Celery Beat на сервере не используется, можно добавить cron:

```bash
0 8 * * * cd /var/www/project/managers_sl && docker compose exec -T web python manage.py send_birthday_reminders
```

## 18. Карточки стран, городов и ВУЗов

В web cabinet каталог открывается через раздел **Вузы**.

1. `/portal/countries/` показывает страны карточками: флаг, описание, количество городов и ВУЗов.
2. `/portal/cities/` показывает города карточками: страна, описание и количество ВУЗов.
3. `/portal/universities/` показывает ВУЗы карточками с обложкой, логотипом, описанием и количеством программ.
4. Кнопка **Открыть** у ВУЗа ведёт на страницу просмотра `/portal/universities/<id>/`, а не на редактирование.
5. На карточке просмотра ВУЗа есть отдельные кнопки **Редактировать** и **Добавить программу**.
6. Внизу карточки ВУЗа показываются его программы. Если программ нет, система показывает подсказку **У этого ВУЗа пока нет программ. Добавьте первую программу.**
7. Программу можно добавить из карточки ВУЗа через кнопку **Добавить программу**.

## 19. Кэш каталога ВУЗов

Каталог ВУЗов и публичный client API кэшируются на короткое время, чтобы страницы открывались быстрее.

Кэш применяется к справочникам и каталогу:

- страны;
- города;
- ВУЗы;
- программы;
- `/portal/universities/`;
- `/api/client/v1/universities/`;
- `/api/client/v1/programs/`.

Персональные разделы, клиенты, финансы, документы, уведомления и рабочий день грубо не кэшируются. При изменении ВУЗа, программы, стоимости, intake, требуемых документов или контактов кэш каталога сбрасывается автоматически.

## 20. Какие старые разделы не использовать

Не создавайте новые рабочие данные в старых приложениях:

- `clients`
- `leads`
- `catalog`
- `services`
- `analytics`
- `documents`
- `tasks`
- `timetracking`
- `notifications`
- `reports`
- `mailing`
- `gamification`
- `support`

Они оставлены как архив и источник данных для миграции. Подробный план очистки находится в `docs/cleanup_old_apps.md`.
